# Security Model & Policy Defaults

OpenAgent Infrastructure operates under a strict defense-in-depth posture tailored for autonomous agents operating on user environments.

---

## 1. Explicit Trust Boundaries

| Subsystem               | Trust Classification     | Role & Authority                                                                                                       |
| :---------------------- | :----------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| **LLM Provider**        | **Untrusted**            | Proposes actions based on stochastic modeling. Has zero authority to authorize executions or bypass gates.             |
| **Policy Engine**       | **Security Authority**   | Deterministic gatekeeper. Authorizes or forbids proposed actions based on explicit policy rules and domain whitelists. |
| **Executor Dispatcher** | **Enforcer**             | Dispatches only verified `ApprovedAction` instances carrying cryptographic approval tokens.                            |
| **Audit Logger**        | **Accountability Layer** | Append-only SHA-256 hash-chained log. Sanitizes secrets before persistence to prevent credential leakage.              |

---

## 2. Default-Deny for Sensitive Actions

The policy engine maintains an internal list of inherently sensitive action primitives:

- `shell_exec`: Arbitrary command-line execution.
- `execute_code`: Dynamic code evaluation (eval/exec/WASM).
- `file_write` / `upload`: Local file creation, modification, or outbound upload.
- `file_delete`: Local file deletion.
- `download_file` / `download`: Uncontrolled file downloading.
- `read_credentials`: Accessing secrets, environment variables, or password fields.
- `submit_payment` / `submit`: Form or transaction submission.
- `network_exfiltrate`: Arbitrary outbound data egress.

**Rule**: If any action classified as sensitive lacks an explicit policy rule granting `ALLOW` or `ASK_USER`, the engine **always defaults to `DENY`**.

---

## 3. Secret Redaction Layer

Audit records and logs automatically pass through `SecretRedactor` before being saved or hashed:

- **Sensitive Key Sanitization**: Keys such as `password`, `token`, `api_key`, `authorization`, `cookie`, `credentials` are masked as `[REDACTED]`.
- **Pattern Redaction**: High-entropy strings including Bearer tokens, OpenAI keys (`sk-...`), and JWT tokens are sanitized via regex scanning.
- **Fail-Safe Integrity**: SHA-256 hash chaining is computed on the sanitized audit payload, preventing raw secrets from existing in the hash history.

---

## 4. Anti-Bypass & Tamper Resistance

1. **Direct Executor Invocation Prevention**:
   The `ExecutorDispatcher` verifies that incoming actions contain a valid `ApprovedAction` structure with an approval token generated by the Policy Engine/Runtime:
   $$\text{token} = \text{HMAC-SHA256}(\text{action.id} \parallel \text{decision} \parallel \text{approvedAt})$$
   Direct or unapproved calls fail closed with a `SecurityViolationError`.
2. **Action Tampering Detection**:
   Any modification to `action.id`, action payload, or parameters after policy evaluation breaks token verification and triggers an immediate abort.
3. **Emergency Stop (Kill Switch)**:
   The operator can trigger `emergencyStop(sessionId)` at any point. The runtime cancels pending actions, sets session state to `STOPPED`, and blocks any subsequent step attempts.
